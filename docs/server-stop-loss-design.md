# 서버: 명령 없이 일어난 청산 반영(거래소 손절 주문의 선행 작업)

- 대상: `gg_parrot` 백엔드(`app/runner.py`, `app/runner_engine.py`, `app/engine/driver.py`)와 이 앱
- 기준: 2026-10-15의 백엔드·앱 코드

## 문제

- 서버는 세션마다 전략 드라이버(`StrategyDriver`)를 돌림.
- 포지션 상태(`in_pos`, 수량, 평단, 쿨다운)는 드라이버가 들고 있음. 드라이버가 낸 체결만 명령이 됨.
- 앱은 서버 명령 없이도 직접 청산함. 로컬 손절·하루 손실 한도·최대 보유시간(`bot/run_loop.rs`의 `enforce_safety_net`).
- 앱은 하트비트마다 보유 상태(`in_position`, 수량 등)를 보냄.
- 서버는 이 값을 세션에 저장하고, 드라이버와 다르면 경고 이벤트(`check_position_mismatch`)를 한 번 남김. 드라이버 상태는 그대로 둠.
- 그 결과 생기는 어긋남:
  - 서버 청산 신호 → 앱에 보유가 없어 건너뜀(`no_position_no_order`)
  - 그리드·마틴게일의 추가 진입 신호 → 앱에서는 새 진입, 서버는 기존 평단에 더해 계산
  - 손절 뒤 쿨다운이 서버 전략에 걸리지 않음
  - 웹의 손익·상태가 서버 기준이라 앱과 다름
- 거래소에 손절 주문(선물 `STOP_MARKET`)을 걸면 앱이 꺼진 동안에도 청산됨. 같은 어긋남이 더 자주, 더 오래 생김.
- 따라서 거래소 손절 주문보다 이 작업이 먼저임.

## 먼저 할 수 있는 최소안(서버만 수정)

- 조건: 앱이 보낸 상태가 보유 없음 + 드라이버는 보유 중 + 대기 중인 청산 명령 없음
- 처리: 드라이버를 마지막 가격으로 비움. 앱 변경 없음.
- 한계:
  - 청산 이유를 몰라 손절 쿨다운을 걸 수 없음
  - 손익이 마지막 가격 기준이라 근사치
  - 일부 청산은 처리할 수 없음
- 어긋남만 먼저 없앨 때 적합. 거래소 손절 주문까지 가려면 아래 정밀안이 필요함.

## 정밀안: 바꿀 것

### 1. 하트비트에 `exits` 추가(앱 → 서버)

- `acks` 옆에 명령 없이 일어난 청산 목록을 실음.

```json
"exits": [
  {
    "exit_id": "ex-<uuid>",
    "reason": "local_stop_loss",
    "qty_frac": 1.0,
    "executed_qty": 0.012,
    "fill_price": 61234.5,
    "ts_ms": 1792030000000
  }
]
```

- `reason`: `local_stop_loss`·`local_force_close`(하루 손실·최대 보유시간)·`exchange_stop`(거래소 손절 주문 체결)
- `qty_frac`: 청산 직전 보유 대비 비율(전량이면 1.0). 일부 청산 뒤 남은 수량을 서버가 맞추는 데 씀.
- `exit_id`: 앱이 만듦. 같은 청산을 다시 보내도 한 번만 반영되게 하는 열쇠.
- 서버가 받았다고 답할 때까지 앱이 다음 하트비트에 다시 실음(지금 `acks`를 보존하는 방식과 같음).

### 2. 서버 처리: `apply_exits`

- `exchange_commands`의 `apply_acks` 다음에 호출.

1. `exit_id`가 중복이면 건너뜀. 받은 id는 세션별로 보관(새 테이블 또는 `RunnerCommand`와 같은 방식).
2. 드라이버에 외부 청산 반영. 드라이버에 메서드 신설.
   - `StrategyDriver.external_exit(qty_frac, price, ts, is_stop)`
   - 안에서 stepper의 기존 청산 경로를 그대로 씀(`is_stop=True`면 쿨다운까지). 새 명령(Fill)은 만들지 않음.
   - 드라이버 조작은 루프 스레드에서 함. 되돌리기(`_apply_rollback`)처럼 `_RollbackJob`으로 넘김.
   - 드라이버가 이 프로세스에 없으면(재기동 중) `state_json`만 고침. 되돌리기의 `""` 경로와 같음.
3. 이 청산으로 의미가 없어진 대기 명령(`pending`) 취소.
   - 전량 청산이면 대기 중인 청산 명령
   - 손절이면 쿨다운 동안의 진입 명령
4. `engine.external_exit` 이벤트를 남기고, `check_position_mismatch`의 경고 기억을 지움.
5. 하트비트 응답에 `accepted_exit_ids`를 실음.

### 3. 하위 호환

- `exits`가 없으면 지금과 같음. 지금 배포된 앱과 서버는 그대로 동작.
- 앱은 응답에 `accepted_exit_ids`가 있으면 서버가 지원하는 것으로 판단.
- 지원하지 않는 서버에서는 거래소 손절 주문을 걸지 않음(어긋남을 늘리지 않게).

## 앱 쪽 작업(서버 1·2가 들어간 뒤)

1. `enforce_safety_net`이 청산하면 `exits`에 넣음(`local_stop_loss`·`local_force_close`).
2. 선물만, 서버가 `accepted_exit_ids`를 지원할 때만 거래소 손절 주문을 걺.
   - 진입 체결 뒤: `STOP_MARKET`, `closePosition=true`, `workingType=MARK_PRICE`. 손절 가격 = 평단 × (1 − 손절%)(숏은 +). 서버 stepper의 손절 식과 같음.
   - 추가 진입·일부 청산 뒤: 취소하고 새 평단으로 다시 걺.
   - 청산·'청산 후 종료': 취소.
   - 다시 연결되거나 다시 켰을 때: 그 주문의 client id로 조회. 체결됐으면 보유를 0으로 하고 `exits`에 `exchange_stop`으로 보고.
3. 현물·국내 거래소는 걸지 않음(국내는 시장가 손절 주문이 없음). 화면에 "앱이 켜져 있을 때만 손절"이라고 안내.

## 정해야 할 것

- '매크로만 종료'로 남긴 포지션의 거래소 손절 주문을 남길지, 취소할지
- 일부 청산(`qty_frac` < 1) 뒤 서버 전략의 평단·그리드 칸을 어떻게 맞출지
  - 1단계는 전량 청산만 받고, 일부 청산은 경고만 남기는 방법도 있음
- 손절 가격을 서버가 정해 진입 명령에 실을지(`stop_price`)
  - 1단계는 앱이 위 식으로 계산

## 완료 기준

- 앱이 로컬 손절한 뒤 다음 하트비트에서 서버 드라이버가 비어 있고, 쿨다운이 걸려 있음.
- 같은 `exit_id`를 두 번 보내도 한 번만 반영됨.
- 그 뒤 서버가 청산 신호를 보내지 않음(`no_position_no_order`가 나오지 않음).
- 서버 재기동 중에 온 `exits`도 `state_json`에 반영됨. 재기동 뒤 드라이버가 비어 있는 상태로 시작함.
