- 착수 전에 항목마다 설계 문서를 따로 쓰고 승인받음.

## 1. 브라우저 로그인으로 앱 연결

**목표.** 회원 키를 복사해 붙여 넣지 않고, 시스템 브라우저에서 로그인해 이 PC를 계정에 연결함(Claude 데스크톱·VS Code 방식).

**흐름.**

1. 앱이 `state`·PKCE `code_verifier`를 만들고 브라우저로 `https://<사이트>/desktop/connect?state=…&code_challenge=…&device_name=…`를 엶.
2. 사이트에서 로그인(이메일·구글) 뒤 "이 PC 연결"을 누르면 `ggparrot://auth?code=…&state=…`로 돌아옴.
3. 앱은 `state`를 대조하고 `POST /api/desktop/token`(`code` + `code_verifier`)으로 기기 토큰을 받아 키체인에 저장함.

**서버(gg_parrot).**

- 연결 페이지, 1회용 코드(60초·한 번만), 코드 교환 API.
- 기기 토큰 테이블: 사용자·기기 이름·만든 시각·마지막 사용·폐기 여부. 토큰은 해시만 저장.
- 웹 설정에 "연결된 PC" 목록과 연결 끊기.
- 실행기 API(`/api/runner/*`)가 회원 키와 기기 토큰을 모두 받게 함(전환 기간).

**앱.**

- 딥링크 `ggparrot://auth` 처리(기존 단일 실행·딥링크 흐름 재사용).
- 설정 › 껄무새 계정: [브라우저로 연결]·연결된 계정·[연결 끊기].
- 회원 키 직접 입력은 "고급"으로 남김.

**보안.**

- PKCE(S256) 필수.
- `state` 불일치는 버림.
- 코드 재사용 거절.
- 토큰은 키체인에만.
- 서버는 토큰 해시만 보관.
- 토큰 폐기 즉시 401.

**완료 기준.**

- 새 PC에서 회원 키 입력 없이 연결·실행·하트비트가 됨.
- 웹에서 연결을 끊으면 다음 요청부터 앱이 "다시 연결" 상태가 됨.

## 2. 앱 안 사이트 창

**목표.** 매크로 만들기·고치기·백테스트는 사이트 화면을 그대로 쓰고, 앱 안 창에서 바로 실행까지 이음(화면 중복 개발 없음).

**설계.**

- 앱이 사이트를 별도 창으로 엶. User-Agent 뒤에 `GGParrotDesktop/<버전>`을 붙임.
- 사이트는 UA를 보고 화면만 바꿈: "실행기 받기" 숨기기, [실행기 열기] → [앱에서 실행].
- UA는 꾸밀 수 있으므로 권한 판단에는 쓰지 않음.
- 로그인은 창 안에서 하지 않음. 구글은 내장 웹뷰 로그인을 막음(`disallowed_useragent`).
- 항목 1의 기기 토큰을 1회용 교환 코드로 바꿔 창의 웹 세션을 엶.
- [앱에서 실행]은 기존 실행 티켓(`ggparrot://launch`) 흐름을 그대로 씀.

**보안.**

- 원격 페이지 창에는 Tauri IPC 권한을 주지 않음(capability를 메인 창으로만 한정한 지금 설정 유지).
- 창이 열 수 있는 주소는 사이트 도메인으로 제한하고, 그 밖의 링크는 시스템 브라우저로 엶.

**완료 기준.**

- 앱 안 창에서 매크로를 고르고 [앱에서 실행]을 누르면 실행 목록에 추가됨.
- 창에서 앱 내부 명령을 부를 수 없음.

## 3. 다른 PC에서 실행 중인 매크로 보기

**목표.** 같은 계정의 다른 PC에서 도는 매크로를 앱에서 "다른 PC" 표시와 함께 봄.

**설계.**

- 서버: `GET /api/runner/sessions`(기기 토큰 인증) — 기존 `runner.list_sessions(user_id)`를 쓰고 실행 중 세션만 냄.
- 서버: 세션에 시작한 기기(항목 1의 기기 ID·이름)를 기록함.
- 앱: 이 앱이 시작한 세션 ID와 다르면 "다른 PC · <기기 이름>" 배지.
- 앱: 처음에는 읽기 전용, 15~30초 간격으로만 다시 부름(창이 보일 때만).
- 원격 종료는 다음 단계로 미룸. 토큰이 새면 남이 세션을 멈출 수 있으므로 웹 확인 절차와 함께 따로 설계함.

**완료 기준.**

- PC 두 대에서 같은 계정으로 실행하면 서로의 실행이 "다른 PC"로 보임.
- 끝나면 목록에서 빠짐.

## 4. 거래소 쪽 손절 주문·거래소 상태 대조

- 주문 경로의 안전장치(진입 전 확인·손절 재시도·결과 조회 연장 등)는 이미 있음.
- 아래는 서버 전략·화면과 함께 정해야 해서 따로 둠.

**4-1. 거래소 쪽 손절 주문(선물).**

- 먼저 서버가 명령 없는 청산을 받아야 함 — [서버 설계](server-stop-loss-design.md).
- 지금 손절은 앱 루프에서만 봄 — PC 잠자기·앱 종료·인터넷 끊김 동안은 손절이 없음.
- 선물은 진입 체결 뒤 `STOP_MARKET`(`closePosition=true`, `workingType=MARK_PRICE`)를 걸고, 청산·부분 청산·종료 때 취소·다시 걺.
- 정할 것: 서버 전략의 추가 진입(그리드·마틴게일)마다 손절 가격을 어떻게 다시 거는지, 일부 청산 뒤 수량, 사용자가 '매크로만 종료'로 남긴 포지션의 손절 주문을 남길지, 서버가 이 주문을 알아야 하는지.
- 현물·국내 거래소는 지원 범위가 달라(국내는 시장가 손절 주문 없음) 화면에 한계를 알림.

**4-2. 거래소 상태 대조.**

- 앱은 시작할 때 보유를 0으로 보고, 결과를 모르는 주문이 생기면 실행을 멈춤.
- 시작할 때·결과를 모를 때 거래소 포지션(선물 `positionRisk`)·잔고를 조회해 맞추면 멈추지 않고 손절만 계속 볼 수 있음.
- 정할 것: 현물 잔고에는 사용자가 따로 산 코인도 섞여 있어 '이 매크로의 보유분'을 가를 수 없음 — 선물만 대조할지, 현물은 경고만 할지.

**4-3. 안전 규칙 상태 저장.**

- 하루 손실·쿨다운·보유 시작 시각이 메모리에만 있어 앱을 다시 켜면 풀림.
- 매크로별로 저장하고 날짜가 바뀌면 지움.

**4-4. 그 밖.**

- 선물 헤지 모드(`dualSidePosition`) 시작 전 확인.
- 현물 시장가 매수를 금액(`quoteOrderQty`)으로 내 상한을 정확히 지키기.
